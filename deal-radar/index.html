RA Deal Radar

Every Monday at 9 AM, Rungta Advisors' analysts get one email with the week's India M&A, private equity and venture deals. I built the pipeline that collects them from nine public sources, works out what each deal is, and writes the email.

The problem

Keeping up with Indian deal flow means checking business news, startup trackers, and exchange and regulator filings, every week. The same deal shows up in five places with different numbers, and the useful part (who bought whom, for how much, at what stage) is buried in prose.

Deal Radar does that sweep automatically and hands analysts one structured summary.

How it works

  1. Collect

    Pulls the week's articles and filings from two RSS feeds, four news sites, and the NSE, CCI and SEBI filing systems. Each source has its own small fetcher, so a site redesign only breaks that one source.

  2. Extract

    A batched LLM call reads each item and fills in a structured deal record: acquirer, target, deal size, type, stage, cross-border direction and advisors. Anything that isn't a real India-connected deal is dropped.

  3. Merge

    Fuzzy matching merges the same deal when several outlets cover it, and updates a deal's stage when it moves from rumoured to announced to completed across weeks.

  4. Write

    Groups the deals into sections (top deals, domestic M&A, cross-border, PE/VC, advisor mandates, rumoured) and renders a branded HTML email.

  5. Send

    Emails the digest to the team and saves state, so a re-run never re-reads or re-sends an article it has already seen.

Decisions I made

It should cost nothing to run

Only free public sources, Gemini's free tier for extraction, and GitHub Actions instead of a server. Calls are paced to the free tier's rate limit, so the weekly run costs $0.

A silent failure is worse than a missing source

BSE's site sits behind bot protection that returns an empty page instead of an error. A scraper would have reported 'no BSE deals' every week, so I left BSE out and documented why.

Structured output, not summaries

The model fills a typed schema (validated with Pydantic) rather than writing free text. That makes deals comparable, mergeable and sortable into the right section.

Remember everything

All articles and deals live in SQLite. The database carries over between weekly runs, which is what makes duplicate merging and stage tracking possible.

What the first run found

43 deals from 308 items. 30 were domestic, 12 were foreign buyers coming into India, and 1 was an Indian company buying abroad. 33 had completed, 7 were announced, 1 had signed a definitive agreement and 2 were still rumours.

What I'd do next

  • Tests for merging. The duplicate-merging bugs I found were caught by reading the output by hand. They should be regression tests.
  • Alerts when a run fails. Today a failed Monday run only shows up in the GitHub Actions tab.
  • Durable storage. GitHub evicts caches after about a week unused, so a skipped week resets merge history. A small hosted database would fix that.
  • BSE through a headless browser, if the extra dependency turns out to be worth it.
